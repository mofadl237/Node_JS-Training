# شرح مخطط علاقات قاعدة البيانات (ERD) - Clinica

## نظرة عامة
تم تصميم قاعدة بيانات Clinica بناءً على نموذج ديناميكي (قابل للإدارة من قِبل الأدمن) وليس enum ثابت. يتيح النظام إضافة التخصصات والخدمات والأسعار والمدد وأوقات العمل دون تعديل كود أو مخطط Prisma.

## الكيانات الرئيسية

### User
يمثل جميع المستخدمين (مريض / طبيب / أدمن). يرتبط بـ Doctor اختياريًا وبـ Appointment كمريض.

### Specialization
جدول ديناميكي للتخصصات الطبية. الطبيب يشير إليه بـ FK. يمكن إيقاف التخصص (isActive) دون حذف السجلات التاريخية.

### Doctor
يمثل ملف الطبيب ويرتبط بـ User (علاقة واحد لواحد) وبـ Specialization. له مواعيد عمل، عروض خدمات، ومواعيد.

### ClinicService
كتالوج عام للخدمات (استشارة، متابعة، إلخ). لا يعني أن كل الأطباء يقدمونه.

### DoctorService
ربط بين Doctor وClinicService مع تحديد السعر (Decimal) والمدة بالدقائق (durationMinutes) وحالة التفعيل. كل طبيب يمكنه تقديم نفس نوع الخدمة بسعر/مدة مختلفين. يُمنع تكرار نفس (doctorId, clinicServiceId).

### DoctorAvailability
فترات عمل يحددها الأدمن (startsAt/endAt). النظام يحسب الأوقات المتاحة بناءً عليها مع مراعاة مدة الخدمة والحجوزات النشطة.

### Appointment
يمثل الحجز الفعلي. يخزن الفاصل الزمني المحجوز snapshots للسعر والمدة وأسماء اختيارية للتقارير التاريخية. لا يتأثر بتغيير الخدمة أو السعر لاحقًا.

## العلاقات
- User 1:1 Doctor (اختياري)
- Specialization 1:N Doctor
- Doctor 1:N DoctorAvailability, 1:N DoctorService, 1:N Appointment
- ClinicService 1:N DoctorService
- DoctorService 1:N Appointment
- User 1:N Appointment (كـ مريض)

## ملاحظات هامة
- استخدام Decimal للأسعار، DateTime للفواصل، snapshots للبيانات التاريخية
- الحجز الديناميكي حسب مدة الخدمة داخل فترات التوفر
- منع التعارض عبر معاملات + قيود قاعدة البيانات
- إلغاء الحجز لا يحجب الوقت للأبد
